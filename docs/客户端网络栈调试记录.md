# 客户端网络栈调试记录

- 记录时间：2026-11
- 对象：某 Unity IL2CPP 手游客户端（Android arm64-v8a，2.7.91）
- 目标：定位客户端网络请求的真实发出点，验证「运行时加载 + 请求改写」的可行性
- 约束：不修改受保护资源；不依赖 root、系统证书或中间人代理

## 一、结论摘要

| 项目 | 结果 |
|---|---|
| 新增 dex / so 参与启动 | 可行 |
| 修改运行时加载的配置文件 | 可行（该文件不在保护清单内） |
| Java 层请求改写 | 可行 |
| C# 层请求改写 | 可行（关键路径） |
| 配置数据重定向 | 不可行（存在来源校验） |
| 端到端链路 | 登录 → 同步 → 主界面 → 进入关卡，验证通过 |

一句话：客户端的网络请求分布在多套栈里，只处理其中一层会出现「部分请求生效、关键请求仍走默认路由」的现象；把改动放在**请求 URL** 这一层，可以同时避开资源校验与配置校验。

## 三、关键发现

### 3.1 三套并行的网络栈

| 通道 | 实现 | 能否被 OkHttp 拦截器改写 |
|---|---|---|
| SDK 认证 | Java / OkHttp | 可以 |
| 游戏网络 | Unity C# 网络层 | 不可以，需 native hook |
| 资源热更新 | UnityWebRequest / 更新器 | 另说 |

早期失败大多源于把三者当成一条通道处理：Java 层看到请求被改写，关键请求却仍然发往默认后端。

### 3.2 配置接口的来源校验

做了三组对照（每次都确认改写确实生效）：

| 提供给客户端的配置 | 结果 |
|---|---|
| 默认域名（http/https） | 正常 |
| 替换成测试后端的原样内容 | 判定为空 |
| 默认配置的原始字节，换到另一个地址 | 同样判定为空 |

结论：客户端会校验配置来源域名，不是默认域名就整份丢弃。"改配置数据"这条路走不通，只能改**请求本身**。

### 3.3 网络配置的真正来源

用探针记录 `_HttpGet` 的参数后，定位到真正决定网关地址的请求：

```
https://game-config.hypergryph.com/api/remote_config/1/prod/default/Android/network_config
https://game-config.hypergryph.com/api/remote_config/1/prod/default/Android/remote_config
https://ak-conf.hypergryph.com/config/prod/official/Android/version
https://ak-webview.hypergryph.com/api/gate/meta/Android?sign=...
```

这四条都由 C# 的 `_HttpGet` 发出，绕过 OkHttp。第一条就是客户端真正使用的网络配置（gs / as / u8 等地址都来自它）。

这也解释了此前所有失败：Java 层虽然改写了配置请求，但 C# 这条仍然拿到默认配置，于是网关始终指向默认后端。

### 3.4 登录状态机时序

真机日志中的顺序（概括）：

```
_SDKLoginImpl → OnSDKLoginFinished → _UpdateSDKIdAndLogin → _PostProcessLoginRequest
_InvokeU8Auth → _FetchExtraDataAfterAuth → _LoginServiceSuccess
```

SDK 认证与账号服务都成功；卡点在 `_PostProcessLoginRequest` 之后——网关登录请求从未构造/发出。

### 3.5 文案归属定位法

遇到「某段提示是不是热更新带来的」这类问题，先在 `global-metadata.dat` 里检索该字符串：命中即为 APK 代码，与资源/Lua 无关。本项目的一个提示文案就是这样确认的。

### 3.6 客户端的四个网络入口

| 方法 | 承载的业务 |
|---|---|
| 网络层 `SendPost`（3 参） | 认证 token |
| 网络层 `SendPost`（4 参） | 认证的另一重载 |
| 网络层 `SendGet`（2 参） | gate meta |
| 网络层 `_HttpGet`（4 参） | network_config / remote_config / version |

对这四个入口做 URL 主机替换后，客户端从测试后端取到配置，随后资源、登录、同步请求均指向测试后端。

## 四、运行时保护组件的校验范围（实测）

为确定可改动边界，做了一组对照：

| 实验 | 结果 |
|---|---|
| 原版包 | 正常 |
| 仅重签名（内容不变） | 正常 |
| 修改核心资源包 | 进程被终止 |
| 修改资源包中的单个字节 | 进程被终止 |
| 新增文件（dex / so / asset） | 正常 |
| 修改某个运行时配置 properties | 正常 |

**观察**：校验集中在核心资源的内容上；新增文件与个别配置文件不在校验清单内；运行期未观察到对代码页的周期性重算。

> 这是针对该版本、该配置的实测结论，不代表通用情况。

### 4.1 符号获取

- `dlopen("libil2cpp.so", RTLD_NOLOAD)` 与 `dlsym(RTLD_DEFAULT, ...)` 在该环境下均失败；
- 可用方案：从 `/proc/self/maps` 找到 `libil2cpp.so` 路径 → 直接解析磁盘 ELF 的 `.dynsym` / `.dynstr` → `st_value + base` 得到地址。

### 4.2 调用时序

- 进程启动早期调用 il2cpp API 会 SIGSEGV/SIGABRT；
- 用「轮询 `il2cpp_domain_get` 直到非空」代替固定延时；`find_class` 前先 `thread_attach`。

## 五、注入方案

| 文件 | 作用 |
|---|---|
| `classes7.dex` | 只含引导类：从应用私有目录加载 `lab.dex`，反射调用入口 |
| `assets/...properties` | 唯一被修改的既有文件：在代理列表末尾追加一个类名 |
| `lab.dex` / `liblab.so` | 实验逻辑，可随时热替换 |

设计动机：包体很大，每次重建 + 签名 + 推送成本高；把逻辑拆到可热替换的两个文件后，迭代从十几分钟降到几十秒。

## 十、经验教训

1. 先分清有几套网络通道，再决定改哪一层。
2. 配置不可重定向时，改请求 URL 往往比改配置数据更稳。
3. `MethodInfo->methodPointer` 替换只对虚调用有效；私有方法多为直接调用，需要 inline hook。
4. inline hook 的跳板要落在目标 ±1GB 内，否则 `ADRP` 无法重定位。
5. 16 字节补丁只能打在足够长的函数上；短函数会被覆盖到相邻代码。
6. 多目标必须各用各的跳板，共用会导致先挂的函数调到后挂的原函数。
7. 探针读字符串前先验证可读性，避免把任意指针当 `Il2CppString` 解引用。
8. 该环境下 il2cpp 符号要靠解析 ELF，`dlopen` / `dlsym` 不可靠。
9. 数据目录为空时，服务端可能「静默降级」：接口仍返回 200，但内容是空的。
10. 排障时先确认「是哪一套网络栈在发请求」，比盯着返回内容有效。
11. UI 卡死时先切一次前后台，排除客户端输入刷新问题。
12. 不要急着相信「热更新导致的」，先用字符串定位法确认归属。
